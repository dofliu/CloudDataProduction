# 學生決策層 —— 讓操作有後果

> 對應 `engine/repair.py`、`api/tickets.py`、`api/maintenance.py`、`api/alarm_rules.py`、
> `web/src/student/DecisionPanel.tsx`。驗證:`tests/test_repair_actions.py`、`tests/test_alarm_rules.py`。

## 為什麼加這一層

在這之前,學生在平台上能做的事幾乎都是**觀察 → 回答數字**:讀值、算統計、填答案、上傳預測。
唯一真的動到世界的是寫 setpoint(CNC 刻字、手臂取放點)。工單的 `resolve` 是按一下就修好,
不需要任何判斷 —— 那是打卡,不是決策。

決策層加的是三件**有代價、且沒有標準答案可抄**的事:

| | 學生做什麼 | 代價落在哪 | 誰是裁判 |
|---|---|---|---|
| 故障處置 | 診斷根因 → 選處置動作 | 選錯 = 白花 60% 工時,設備仍是壞的 | 引擎的隱藏 health |
| 預防保養 | 決定何時停機保養什麼 | 保養停機**計入可用率損失** | OEE 累積器 |
| 告警規則 | 設一條門檻規則交平台代跑 | 太敏感 → 誤報;太鈍 → 漏報 | 真實故障起始時刻 |

三件事共通的性質:**做對做錯的差別由引擎誠實反映出來,不是老師改分數改出來的**。
也因為是取捨題(尤其保養),AI 代寫代不了 —— 它可以幫你寫 client,但替不了你決定要不要停機。

## 一、故障處置要選對動作

### 工單不寫根因

學生視圖的工單**拿掉了 `component` 與 `fault_type`**(`api/tickets.py` 的 `_redact`),
只留 `symptom`。教師身分才 reveal 根因。理由很簡單:工單上寫著「spindle_bearing 失效」
就等於把答案印在考卷上。

學生看得到的是:哪台設備、跳機了、什麼時候跳的。要判斷根因,只能去看那台設備的遙測。

### 維修手冊是教材

`GET /api/repair/actions` 公開八個動作,每個都附 `signature` —— **這種故障在數據上長什麼樣**:

| 動作 | 工時 | 數據上的徵候 |
|---|---|---|
| 更換軸承 | 6h | 振動 RMS 持續走高,常伴隨溫度上升 |
| 更換磨耗件 | 3h | 切削力 / 扭矩 / 電流緩步上升,良率下滑,振動變化不明顯 |
| 清潔濾網 | 2h | 壓差或出口壓力上升、流量下降,溫度跟著爬 |
| 液壓 / 真空 / 潤滑保養 | 5h | 壓力建立變慢、洩漏率上升、循環時間拉長 |
| 製程參數校正 | 4h | 製程量測整體偏移,但機構訊號正常 |
| 更換電氣元件 | 5h | 電流 / 功因 / 絕緣異常,機械訊號正常 |
| 感測器校正 | 1.5h | 單一訊號與其他相關訊號**脫鉤** |
| 整機大修 | 24h | 萬用解,一定成功,停機最久 |

這張表本身就是 docs/02 訊號模型的教學版本:學生要學會「振動走高」與「壓差上升」與
「讀值脫鉤」是三種不同的東西。它不含「哪台該用哪個」,所以給出去不會洩答案。

### overhaul 是刻意留的出口

診斷不出來可以直接大修,一定修好 —— 但停 24 小時,可用率會很難看。
**可以不診斷,但要付錢**,這件事本身就值得教。學生第一次靠大修過關、第二次發現排名掉下去,
比講十遍「診斷很重要」有效。

### 選錯會怎樣

`device.repair(action)` 只修對症的元件。選錯時:

- 設備**仍然是壞的**(`_fault_latched` 不解除)。
- 仍佔用 60% 的工時 —— 拆開才發現不是這裡,時間一樣花掉了。
- 工單退回 `acked`,`wrong_attempts` +1,計分榜多一欄「誤修」。
- 維修工時未結束前不接受下一次處置(不能連點刷次數繞過代價)。

維修期間設備狀態是 `maintenance`(現場的事實是有人在拆它);工時結束若沒修好,
狀態誠實翻回 `fault`。

> **一次故障只開一張單**:因為進出維修會讓 state 在 `maintenance` / `fault` 之間來回,
> 故障事件改看**故障閂鎖的上升緣**而不是 state 字串(`engine/world.py` 的 `_detect_events`)。
> 這件事有測試守著(`tests/test_repair_actions.py` 第 5 項)。

## 二、預防保養:停機換壽命

`POST /api/maintenance {device, action}`,需要認領授權(只能保養自己公司的設備)。

- 對症 → 該元件修回 `health ≈ 0.98`,回傳 `health_gain`(這次買到多少壽命)。
- 不對症 → `health_gain = 0`,但工時照收。學生會看到「白花」兩個字。
- **一律停機,且計入可用率損失**(`engine/device.py` 的 `_accumulate_oee`)。

保養不計入可用率的話,最優策略就是每天保養一次,那沒東西可教。計入之後,學生面對的是:

> 現在停 3 小時換刀,還是賭它撐到下週?撐過去 OEE 漂亮,賭輸了是 6 小時停機加良率損失。

這題沒有標準答案。平台不另外給「保養分數」—— 那只會鼓勵學生刷次數;
保養做得好不好,已經誠實地反映在 `/api/oee` 的可用率上了。

## 三、託管告警規則:手機就能做的預警

階段二要學生寫一支服務訂閱遙測、跑模型、`POST /api/predictions`。那對跟得上的人很好,
但要學生的機器一直掛著,而且課堂當下(只有手機)做不到。

託管規則讓學生只交一條規則,平台代跑:

```
POST /api/alarm_rules
{"device": "c01-cnc-01", "tag": "vibration_rms",
 "agg": "ema", "window_s": 3600, "op": ">", "threshold": 4.5, "for_s": 1800}
```

意思是:vibration_rms 的一小時移動平均超過 4.5,**持續半小時**才告警。

### 評分怎麼算(對 ground-truth)

- **命中**:告警之後 24 模擬小時內,那台設備真的故障。
- **誤報**:告警後視窗內沒有故障。
- **漏報**:你監控中的設備壞了,但你沒叫。沒下規則的設備壞掉不算你的漏報。
- **重複**:同一次故障的第二、三則告警,不計分也不算誤報(不然「一直叫」就能刷 recall)。
- 輸出 precision / recall / F1 / 平均提前量,上排行榜。

### 兩個刻意的設計

**條件要持續 `for_s` 才叫**,而且**條件解除後才重新武裝**。少了這兩件,一碰門檻就叫的規則
會在雜訊上洗出上百則告警;學生要學的正是「告警不是越靈敏越好」。

**移動平均用 EMA(指數移動平均),時間常數 = `window_s`,不是等寬視窗平均。**
這件事寫在 API 回傳與這份文件裡 —— 學生在家用 pandas `rolling(...).mean()` 算會跟平台略有出入,
那是要教的取樣 / 濾波差異,不是 bug。

## 課程對應

| 週 | 原本 | 加上決策層之後 |
|---|---|---|
| W6 異常的資料特徵 | 找出被動手腳的設備 | 找出來之後**還要判斷是哪一類**,選對動作 |
| W8 多訊號關聯 / 資料品質 | 寫一頁報告判斷是感測器還是製程 | 判斷錯的代價是真的白花工時 —— 紙上判讀變成有後果的決定 |
| W11 KPI / OEE | 算 OEE 跟平台對答案 | 你的保養決策**造成**這個 OEE,不只是算它 |
| W13 趨勢 / 預警 | 選作:寫服務 POST 預測 | 必做的低門檻版:交一條規則,一樣算 F1 與 lead time |

## 教師面

- `GET /api/tickets` 帶教師身分 → reveal 根因,對照學生選了什麼動作。
- `POST /api/session/reset` 新增 `maintenance` / `alarm_rules` 兩個可清項目(預設清)。
- 計分榜新增 `wrong_repairs`(誤修次數);誤修每次 −10 分,漏報仍是 −30。
