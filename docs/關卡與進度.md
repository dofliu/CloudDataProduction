# 資料的一生 —— 九關與全班進度看板

> 對應 `scenarios/levels.yaml`、`api/levels.py`、`adapters/access_log.py`、
> `web/src/student/LevelsPanel.tsx`、`web/src/teacher/LevelBoard.tsx`。
> 驗證:`tests/test_levels.py`。

## 這一層解決的問題

60 人、無助教,批改早就自動了 —— 真正難的是**看不到誰卡住**。
作業一次一次交,誰交了幾份、卡在哪一步,老師要自己拼。

關卡把課程主軸「資料的一生」變成一條**可見的進度線**:學生知道自己走到哪、下一步做什麼;
老師一張格子牆就知道「12 個人卡在 OPC-UA」。

## 為什麼不另創遊戲劇情

課程主軸本來就是九個階段:

```
產生 → 接取 → 串流 → 儲存 → 統計 → 視覺化 → KPI → 預警 → 報告
```

另外發明一套關卡故事只會跟課程打架,還多一份東西要維護。
**這九關就是那九個階段,過關條件就是課程本來就要交的東西** —— 關卡是外殼,不是新作業。

| 關 | 週 | 通關條件 | 判定方式 |
|---|---|---|---|
| 產生 | W1 | 認領一間公司 | 查認領狀態 |
| 接取 | W2 | `connect` 作業通過 | 對即時真值容差計分 |
| 串流 | W10 | `events` 作業通過 | 對事件時間軸比對 |
| 儲存 | W7 | `aggregate` 作業通過 | 對 historian 重取樣真值 |
| 統計 | W4 | `stats` 作業通過 | 對時間窗統計真值 |
| 視覺化 | W4 | 課堂 demo | **教師勾**(誠實標示為人工) |
| KPI | W11 | `oee` 作業通過 | 對 OEE 累積器 |
| 預警 | W13 | 告警 F1 ≥ 0.5 **或** 預測命中 ≥ 1 | 對真實故障起始時刻 |
| 報告 | W18 | 期末專題 | **教師勾** |

支線徽章(不擋主線,把「決策做得好」單獨標出來,見 [決策與後果.md](決策與後果.md)):
**一次修好**(結案過工單且零誤修)、**防患未然**(3 次有效保養)、**零誤報**(有命中且零誤報)。

## 誠實性:學生說「我做完了」沒有用

通關判定**一律現查平台手上的事實**,`api/levels.py` 不快取任何進度狀態(鐵則一)。
唯一被存下來的是「教師勾了哪幾格」。

兩關本質要人看(儀表板 demo、期末報告),就誠實用 `kind: manual` 標成人工判定 ——
與其發明一個假的自動判準,不如老實說這關是老師認的。而且**人工勾選不能拿去勾自動關卡**
(`mark()` 會擋),不然關卡就變成人情。這條有測試守著。

## 瓶頸關的算法

教師看板上的「瓶頸」**不是**「沒過的人最多的那一關」—— 那永遠是最後一關,沒有資訊量。

算的是:**前一關過了、這一關沒過**的人數。已經走到門口卻進不去的,才是真的卡住,
也才是老師下一節課該補的東西。

## 協定端存取軌跡

`adapters/access_log.py` 記錄「哪台設備被工業協定讀了幾次、平均多久打一次」。
Modbus 走 datastore 的讀取攔截(`_TrackedBlock`),引擎自己反射設定點的讀回不算。

用途有三,**通關判定不在其中**:

1. **教材**:W2 教接取、W10 教輪詢 vs 訂閱時,把學生自己的足跡投影出來 ——
   「你這支 client 每 0.2 秒打一次,一天 43 萬次請求,你真的需要嗎?」
2. **佐證**:學生的關卡頁會顯示「你的設備被 Modbus 讀了 N 次」,教師面也看得到。
3. **可選條件**:`levels.yaml` 支援 `kind: access`,教師若確定班上一人一廠、不互相讀,
   可以拿它當通關條件。

### 一個要講清楚的限制

pymodbus 的 datastore **拿不到 client 位址**,所以這一層記的是「哪台設備被讀了」,
不是「哪個學生讀的」。班上任何人都能讀任何一台(設備目錄本來就公開)。

因此預設的九關**不用**存取軌跡當通關條件 —— 通關看的是學生自己交出來、對得上 ground-truth
的數字,那個假不了。這個限制寫在程式碼註解、API 回傳的 `note` 欄位,以及這裡,
免得有人以為平台能證明「這個學生真的寫了 client」。

## API

| 方法 | 路徑 | 權限 | 說明 |
|---|---|---|---|
| GET | `/api/levels` | 公開 | 關卡與徽章定義(含提示) |
| GET | `/api/levels/{student}` | 公開 | 某學生的過關狀態 + 佐證 + 下一關 |
| GET | `/api/levels/board/all` | 教師 | 全班 N×9 矩陣 + 每關過關人數 + 瓶頸關 |
| POST | `/api/levels/mark` | 教師 | 勾選人工關卡 `{student, level, done}` |
| GET | `/api/access_log` | 公開 | 協定端存取軌跡(次數 / 平均間隔) |

## 要改關卡就改 YAML

`scenarios/levels.yaml` 是唯一的定義來源,加關、換條件、調門檻都在那裡改,
`api/levels.py` 不寫死任何一關。判定方式有 `claim` / `submission` / `access` / `tickets` /
`maintenance` / `alarm` / `prediction` / `manual`,以及 `any` / `all` 組合。
新增判定方式要同步更新 `tests/test_levels.py` 的 `KNOWN_KINDS`,CI 會擋下打錯字的 `kind`。
