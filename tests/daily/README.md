# 每日模擬測試

每天跑一個**操作情境**,產出一份圖文報告,回答:**在這個狀況下,平台的資料與畫面還正確嗎?**

與 `tests/animation`(驗「畫面有沒有對應到資料」)分工不同 —— 這裡驗的是
**「把平台放進各種課堂會遇到的狀況,資料本身還說得通嗎」**。

```bash
bash tests/daily/run_all.sh                 # 依今天日期輪替情境
bash tests/daily/run_all.sh --key disaster_day   # 指定情境
bash tests/daily/run_all.sh --date 2026-09-15    # 指定日期(看那天會輪到哪個)
```

產出 `artifacts/daily/report.html` —— **自包含**:截圖用 data: URI 內嵌,可離線開、
可直接發布、可寄出去,不依賴任何外部主機(校內 LAN 無外網也看得到)。

## 情境怎麼輪

`scenarios.yaml` 列出 10 個情境,依 `日期序數 % 情境數` 輪替:

- 同一天重跑 → **同一個情境**(可重現,出問題查得回去)
- 不同天 → 走到不同情境,約十天把「學生會遇到的狀況」掃過一輪

情境涵蓋:正常基線、夜間非上班、突發設備故障、漸進退化、感測器漂移、教師停機、
災難日、良率型 subtle fault、廠務異常、長時間 run-to-failure。

每個情境帶一組 `expect`,跑完逐條判定。想加情境就編 `scenarios.yaml`,不用改程式
(除非要新的判定型式)。

## 判定分三級

| 級別 | 意義 |
|------|------|
| **PASS** | 通過 |
| **已知** | 失敗,但已登記在 `scenarios.yaml` 的 `known_issues` —— 報告標琥珀色 |
| **FAIL** | **新**問題,報告標紅、腳本離開碼 1 |

分級的理由:一個從第一天就整片紅的監控工具,會把人訓練成忽略它。
紅色要留給**新出現**的問題。修好某個已知問題後,把 `known_issues` 裡那筆刪掉即可。

## 判定型式

| `expect` 欄位 | 驗什麼 |
|---|---|
| `any_fault` | 應該 / 不應該有設備進入 fault |
| `all_running` | 所有 producer 都該運轉 / 都該停著(夜間) |
| `stopped_still` | 教師停機的設備,動作類 tag 必須不再變動 |
| `trend_up` / `trend_down` | 被注入的設備上,某 tag 是否有明顯趨勢 |
| `decouple` | 兩個訊號脫鉤(如濾網阻塞:電流↑ 但流量↓)—— W8 的教學重點 |
| `sensor_marked` | 感測器故障有被記成 sensor 型,而不是設備故障 |

另有三條**不分情境**都要成立的:沒有 NaN/Inf、累積量只增不減、
故障的設備不可以還在生產(速率類 tag 歸零 + 不再計件)、手臂末端座標與六軸角度一致。

## 為什麼截圖是「前 / 後對照」

退化類的情境,單張看不出「東西在變壞」。報告拍觀測窗的開頭與結尾各一張,
擺在一起才讀得出差異。截圖用的是**同一份引擎資料**(`web/preview/frames_daily.json`)——
既拿去判定、也拿去畫面,不是另外造一組給報告看的。

拍攝對象會**優先選被注入 / 被停機的那一台**,不是隨便挑一台正常的。

## 檔案

| 檔案 | 做什麼 |
|---|---|
| `scenarios.yaml` | 情境目錄 + 已知問題登記 |
| `run_daily.py` | 引擎面:跑情境、判定、吐 `result.json` 與 `frames_daily.json` |
| `shoot_daily.mjs` | 畫面:重播當天資料,逐台前後對照截圖 |
| `build_report.py` | 組成自包含 HTML 報告 |
| `run_all.sh` | 一鍵跑完上面四步 |
